# ML-KEM conformance

Verified on 2026-08-17 on the board described in [hardware.md](hardware.md),
running ESP-IDF v5.5.5 and mlkem-native v2.0.0.

## Why this comes before the benchmarks

An implementation that is wrong will still appear to work. If the ESP32 and the
Raspberry Pi both run the same faulty ML-KEM, they agree on a shared secret,
AES-GCM decrypts, the sensor data arrives, and nothing looks amiss. A weak RNG,
a swapped byte encoding or a mis-wired parameter set all survive an end-to-end
demo untouched.

Interoperability proves two implementations agree with each other. Only vectors
produced independently of the implementation prove agreement with FIPS 203.

mlkem-native ships its own test vectors, and they are not those vectors: they
are generated by mlkem-native. Checking the library against them establishes
internal consistency and nothing more. The vectors used here come from NIST's
own ACVP-Server repository.

## Result

```
=== ML-KEM ACVP conformance (v1.1.0.43) ===
ok    ML-KEM-512 keyGen  25/25 vectors
ok    ML-KEM-512 encap   25/25 vectors
ok    ML-KEM-512 decap   10/10 vectors
ok    ML-KEM-512 ekCheck 10/10 vectors
ok    ML-KEM-512 dkCheck 10/10 vectors
ok    ML-KEM-768 keyGen  25/25 vectors
ok    ML-KEM-768 encap   25/25 vectors
ok    ML-KEM-768 decap   10/10 vectors
ok    ML-KEM-768 ekCheck 10/10 vectors
ok    ML-KEM-768 dkCheck 10/10 vectors
ok    160 of 160 ACVP vectors
```

Alongside them, a consistency self-test that the ACVP vectors do not cover:

```
ok    ML-KEM-512  pk=800 ct=768  shared secrets agree
ok    ML-KEM-768  pk=1184 ct=1088  shared secrets agree
ok    tampered ciphertext -> different secret (implicit rejection)
```

The last line checks that flipping one bit of the ciphertext changes the
decapsulated secret. ML-KEM rejects implicitly: decapsulation still returns
success and still produces 32 bytes, derived from the secret key's rejection
value instead. An implementation that ignored the ciphertext entirely would pass
a naive round-trip test and fail this one.

## What is covered, and what is not

| ACVP group | Vectors | Status |
|---|---|---|
| `keyGen` (AFT) | 25 per level | run |
| `encapsulation` (AFT) | 25 per level | run |
| `decapsulation` (VAL) | 10 per level | run |
| `encapsulationKeyCheck` (VAL) | 10 per level | run |
| `decapsulationKeyCheck` (VAL) | 10 per level | run |

Every ACVP group defined for ML-KEM-512 and ML-KEM-768 is executed.

The two key-check groups are the ones that stop being academic the moment a key
arrives over a network instead of out of a header. They cover the input
validation from FIPS 203 §7.2: a public key whose coefficients are not
canonically reduced, or a private key whose embedded public-key hash does not
match, must be rejected rather than quietly processed.

Each group is half valid and half malformed keys. That matters: an
implementation that always answers "invalid" scores 50%, and so does one that
always answers "valid". Only a check that actually discriminates passes.

ML-KEM-1024 is out of scope; see [roadmap.md](roadmap.md).

## Test data provenance

Source: [usnistgov/ACVP-Server](https://github.com/usnistgov/ACVP-Server),
tag `v1.1.0.43`, files under `gen-val/json-files/`:

- `ML-KEM-keyGen-FIPS203/{prompt,expectedResults}.json`
- `ML-KEM-encapDecap-FIPS203/{prompt,expectedResults}.json`

The encapDecap file supplies the encapsulation, decapsulation and both key-check
groups.

The SHA-256 of each input file is recorded in the header of the generated
`firmware/esp32s3-dut/main/acvp_vectors.h`, so the committed test data can be
audited without network access and regenerated byte-for-byte:

```bash
python3 tests/acvp/generate_kat_header.py \
    --acvp-dir <downloaded-acvp-files> \
    --out firmware/esp32s3-dut/main/acvp_vectors.h
```

One detail worth recording: ACVP supplies the key generation seeds `d` and `z`
as separate fields, while mlkem-native takes a single 64-byte `coins` buffer.
The order is `d || z`, confirmed in `mlkem/src/kem.c`, where the second half is
stored as the implicit-rejection value inside the decapsulation key. Reversed,
all 50 keyGen vectors fail — loudly, which is the good case.

## Footprint

Measured from the linked binary as features were added:

| Build | Binary (bytes) | Delta |
|---|---|---|
| Bring-up, no cryptography | 201,584 | — |
| + ML-KEM-512 and ML-KEM-768 | 217,616 | +16,032 |
| + 160 ACVP vectors | 591,984 | +374,368 (test data) |

The +16,032 bytes cover both parameter sets including the shared Keccak code.
The test vectors are `.rodata` and belong to the verification build only; they
will not be present in the protocol firmware.

## Configuration notes

Two settings this depends on, both in `sdkconfig.defaults`:

- `CONFIG_SPIRAM_USE_CAPS_ALLOC=y` keeps cryptographic buffers in internal SRAM
  (see [hardware.md](hardware.md)).
- `CONFIG_ESP_MAIN_TASK_STACK_SIZE=32768`. The ESP-IDF default is 3584 bytes,
  which an ML-KEM-768 secret key plus working buffers overruns without warning.
  Peak stack is a quantity to be measured in v2, not one to be found by lowering
  this until the board stops crashing.

## Reproducing

```bash
. ~/esp/esp-idf/export.sh
cd firmware/esp32s3-dut
idf.py set-target esp32s3
idf.py -p <port> flash monitor
```

The serial port name is assigned by macOS per USB socket and changes when the
board is moved to a different one — it has already been both `usbserial-1410`
and `usbserial-1420` here. Find the current one with `ls /dev/cu.usbserial*`.
